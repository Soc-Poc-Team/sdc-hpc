## Perform common operations

The following procedures cover recurring administrative and workload tasks. Run
configuration and image-building commands on the computer that contains your
checkout of the `small-data-cluster` repository.

### Add a user

The project creates the users listed in the cluster configuration as Linux
accounts on every node. It also permits those users to sign in to JupyterHub and
gives each account a shared home directory under `/homes`. Accounts cannot be
added to a running cluster permanently with commands such as `useradd`.

To add a user:

1. Choose a username and a numeric user ID (UID) that are not already present in
   the configuration. The UID identifies the owner of files, so it must be
   unique.
2. Enter the project development environment on the build computer if you are
   not using `direnv`:

   ```console
   nix develop
   ```

3. Generate a password hash:

   ```console
   mkpasswd --method=sha-512
   ```

   Enter the user's password when prompted. Copy the complete result, which
   begins with `$6$`. The value is a password hash, not the password itself.

4. Add an entry to the `users` section of `config.toml`. For example:

   ```toml
   [users.ture]
   passwordHash = "<PASSWORD_HASH>"
   uid = 5003

   sshKeys = [
     "ssh-ed25519 <PUBLIC_KEY> ture@computer"
   ]
   ```

   Replace `<PASSWORD_HASH>` with the generated hash and `<PUBLIC_KEY>` with the
   public part of Ture's SSH key. You may omit `sshKeys` if the user will not
   sign in over SSH.

   If the deployment uses an encrypted SOPS configuration instead of
   `config.toml`, edit that encrypted configuration as described in
   [Use an encrypted JSON file](#use-an-encrypted-json-file).

5. Rebuild all images from the updated configuration:

   ```console
   ./build-batch.sh
   ```

   Use `./build-batch.sh --impure` when building with the encrypted
   configuration backend.

6. Shut down the cluster, reflash the headnode and every worker drive, and start
   the headnode before the workers. Follow [Flash the images](#flash-the-images)
   for the complete procedure and its data-loss warnings.
7. Sign in to the rebuilt headnode and verify the account:

   ```console
   id ture
   ```

   The output should show Ture's configured UID and membership in the `wheel`
   and `smalldatacluster` groups.

> **Security warning:** Every configured user is currently a member of `wheel`
> and can gain administrative privileges with `sudo`. Only add people who are
> trusted to administer the entire cluster. Never put a plaintext password or a
> private SSH key in the configuration.

### Remove a user

Users exist only because they are part of the configuration built into the node
images. Removing a user therefore follows the same image-based process as adding
one.

To remove a user:

1. Remove the complete `[users.<username>]` entry from `config.toml`, or remove
   the corresponding object from the encrypted SOPS configuration.
2. Rebuild all images from the updated configuration:

   ```console
   ./build-batch.sh
   ```

   Add `--impure` when using the encrypted configuration backend.

3. Shut down the current cluster. This ends its jobs and discards its RAM-backed
   files together with the rest of its runtime state.
4. Reflash the headnode and all worker drives with the newly built images. Start
   the headnode, and then start the workers.

### Shut down nodes with `sdc-hitman`

Use `sdc-hitman` to remove one or more nodes from service and power them off.
The tool performs the following actions:

1. Resolves the requested names against the nodes registered with Slurm.
2. Displays the matched nodes and asks for confirmation.
3. Marks them as `DRAIN`, which prevents Slurm from assigning new work.
4. Waits until their allocated CPUs are no longer in use.
5. Marks them as `DOWN` and, by default, removes their dynamic Slurm records.
6. Connects to each node over SSH and runs the shutdown command.

First, use `sinfo -N` to find the exact node names. Then shut down a worker, for
example:

```bash
sudo sdc-hitman worker-a1b2c3d4e5f6
```

Review the printed target list. Enter `y` only when it contains the nodes you
intend to stop. A normal invocation waits for current allocations, so it may
appear inactive while a job is still running. Use `squeue` in another terminal
to inspect those jobs.

The tool accepts `*` patterns. Quote a pattern so that the shell passes it to
`sdc-hitman` instead of expanding it as a filename:

```bash
sudo sdc-hitman 'worker-*'
```

Worker names generated by the current images begin with `worker-`, followed by a
value derived from a network-interface address.

After all workers are off, shut down the headnode separately:

```bash
sudo sdc-hitman headnode
```

Shutting down the headnode ends access to Slurm, NFS, JupyterHub, Grafana, and
the other central services. Copy required files out of `/homes` before this step
because the live system stores that directory in RAM.

> **Warning:** The `--now` option skips the wait for active allocations. It can
> terminate running jobs and cause incomplete output or data loss. Use it only
> when an immediate shutdown is required and the consequences are acceptable.

The `--dirty` option leaves the nodes registered with Slurm after marking them
`DOWN`. The normal operation removes the dynamic records, and nodes register
again when their images boot. Use `--dirty` only when you intentionally need to
retain the records for diagnosis.

If the command reports `No nodes matched.`, compare the supplied name with
`sinfo -N`. If it fails during the final SSH step, the node may already be
offline or SSH access may not permit the shutdown command. Check the physical
machine before repeating the operation.

### Submit a Slurm batch script

A batch script is a text file containing shell commands and `#SBATCH` lines. The
`#SBATCH` lines request resources from Slurm. `sbatch` submits the script and
returns immediately; Slurm runs it when the requested resources become
available.

The following example creates an array of 50 short tasks. Each task requests one
CPU and 64 MiB of memory, runs for approximately 10 to 25 seconds, and writes a
separate log file:

```bash
#!/usr/bin/env bash
#SBATCH --job-name=tensec_array
#SBATCH --array=1-50
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=64M
#SBATCH --time=00:01:00
#SBATCH --output=logs/%A_%a.out
#SBATCH --distribution=block:cyclic

duration=$((RANDOM % 16 + 10))
end=$((SECONDS + duration))

mem=""

for ((i=0; i<duration*2000; i++)); do
  mem+=$(printf "%1024s")
done

while [ $SECONDS -lt $end ]; do
  mem="${mem:1}${mem:0:1}"
done

echo "Task $SLURM_ARRAY_TASK_ID finished on $(hostname)"
```

To run it:

1. Save the example as `example-array.sh` in your shared home directory.
2. Open a terminal on the headnode and change to that directory.
3. Create the output directory before submitting the job. Slurm must be able to
   open the output files before the script begins:

   ```console
   mkdir -p logs
   ```

4. Submit the script:

   ```console
   sbatch example-array.sh
   ```

   Slurm prints a message similar to `Submitted batch job 1`. The number is the
   job ID. One submission creates 50 array tasks numbered 1 through 50.

5. Watch the queued and running tasks:

   ```console
   squeue --me
   ```

   `PD` means pending and `R` means running. Pending tasks are normal when the
   cluster does not have enough free CPUs or memory to run all tasks at once.

6. After the tasks finish, inspect their output:

   ```console
   ls logs
   head logs/<JOB_ID>_1.out
   ```

   Replace `<JOB_ID>` with the number printed by `sbatch`. The first number in
   each filename is the array's job ID; the second is the array task ID.

To cancel the entire array before it finishes, run:

```bash
scancel <JOB_ID>
```

The example intentionally consumes CPU and memory to demonstrate scheduling. Do
not use it as a performance benchmark.

### Run a computation with Dask

[Dask](https://docs.dask.org/) distributes Python work across multiple processes
or machines. In the current `small-data-cluster` configuration, the headnode
starts a Dask scheduler on its Tailscale interface at port `8786`. Each worker
node starts a Dask worker and connects to that scheduler. The Dask dashboard is
available from the headnode dashboard on port `8787`.

The scheduler coordinates work but does not normally perform the computation.
The workers execute submitted tasks and return their results. The project's
**Python 3.13 small-data-cluster** Jupyter kernel contains the required Dask and
Distributed Python packages. The ordinary command-line Python environment is not
the documented interface for this operation.

Open JupyterHub, create a notebook that uses the
`Python 3.13 small-data-cluster` kernel, and run the following code in a cell:

```python
from dask.distributed import Client

client = Client("tcp://headnode:8786")

numbers = range(10)
futures = client.map(lambda value: value * value, numbers)
results = client.gather(futures)

print(results)
client.close()
```

The expected result is:

```text
[0, 1, 4, 9, 16, 25, 36, 49, 64, 81]
```

While a computation is active, open **Dask Worker Dashboard** from the main
dashboard to see connected workers, running tasks, memory use, and task
progress. If the client cannot connect, verify that the cluster lists worker
nodes and check the scheduler on the headnode:

```bash
systemctl status dask-scheduler
```

Run the following command on an affected worker node:

```bash
systemctl status dask-worker
```

> **Important:** The current Dask workers are persistent system services. Dask
> tasks do not pass through Slurm and do not request Slurm allocations. Dask and
> Slurm workloads can therefore compete for the same worker CPU and memory.
> Coordinate their use and monitor available resources when both systems are
> active.
